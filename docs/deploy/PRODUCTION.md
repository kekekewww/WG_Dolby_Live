# PRODUCTION：正式站部署

依據：規格 §15.1–§15.4、§17、M1-PLAN §7.5。範圍：M1。正式站目前是 `https://sounds.wgstudiomusic.com/`（Astra + Elementor + WooCommerce，時區 Asia/Taipei）。

這份文件**只描述步驟**。任何寫入正式站的動作（上傳外掛、啟用、建立或發布頁面、改選單與首頁、切換模式）都需要管理者**明確授權**。沒有授權就停在 staging，不要自行判斷「應該可以」。

M1 部署的是示範體驗：示範影音（示範影片與示範音訊）不是 Binaural／Atmos 驗證素材，沒有驗票與播放授權。不得對外描述成「付費直播已安全上線」。

### 絕對不做

- **不要將 staging 的整份資料庫覆蓋正式站。** 正式站持續新增會員與訂單，覆蓋會遺失資料。這次只部署：外掛、核可的新頁面、必要設定（規格 §15.2）。
- 不改父主題；不改 Elementor Site Settings；不重建整份 Header。
- 不碰 WooCommerce 的購買按鈕、價格、付款流程、訂單狀態與共用商品模板。
- 不用正式帳戶或真實付款做測試；不建立測試訂單。
- 不把 PHP 貼進文章或頁面；不安裝來源不明的外掛。
- 不在每次請求 flush rewrite；只有確實變更路由時才重建永久連結（規格 §15.3）。
- 不在活動播放中刪除仍可能被舊頁引用的外掛檔案。

## 2. 驗證 ZIP（步驟 2 之前做）

```bash
# 在 ZIP 所在資料夾
sha256sum -c wg-live-<version>.zip.sha256
```

```powershell
# Windows PowerShell：兩行輸出必須完全相同
(Get-FileHash .\wg-live-<version>.zip -Algorithm SHA256).Hash.ToLower()
(Get-Content .\wg-live-<version>.zip.sha256).Split(' ')[0]
```

核對三件事並寫進部署紀錄：

1. 檔名中的版本。
2. SHA-256 與 staging 通過紀錄上寫的**完全相同**。
3. 安裝後「部署資訊」畫面顯示的版本與 build 檔案 SHA-256，和本機 `plugin/wg-live/assets/dist/build-info.json` 一致。

不同就停止；不要使用「看起來一樣」的另一份 ZIP。

**上傳大小前置檢查（步驟 2 之前）。** ZIP 內含兩支示範影片，整包大小約 1.75 MiB（`check:artifact` 有總大小上限），仍可能逼近主機預設的 2 MB 上傳上限。到「媒體 → 新增」（或「工具 → 網站健康狀態 → 資訊 → 媒體處理」）讀取**最大上傳檔案大小**，必須大於等於 ZIP 位元組數（`ls -l` 或檔案內容屬性）。不足時，後台上傳會失敗而且什麼都沒安裝：改用 SFTP 安裝（第 5 節步驟 2 與第 8 節），不要自行去改正式站的 PHP 設定。本機 `test:zip-install` 以 WP-CLI 安裝，不會測到這個上限。目前 ZIP 的 SHA-256 與大小見 `docs/deploy/records/` 最新交接紀錄。

## 3. 對照：部署前後要比對的頁面

同一個 viewport（建議 1440×1000 與 390×844）、登出狀態，在部署前先截圖：Homepage、Store、一個商品頁、Account、Cart、Checkout。部署後再截一次比對（規格 §13.3）。只截圖，不下單。

**效能基準（必須在第 4 節步驟 2 之前取得）。** 外掛一旦啟用，就會在首頁載入 `wg-live-featured.css`（不論部署模式），所以首頁的「沒有外掛」基準在啟用後就拿不到了。部署前先取得：登出、無痕視窗、桌面與手機各一次，Home 與 `/live/`（若 `/live/` 尚不存在，只量 Home）的實驗室 LCP、CLS 與傳輸大小（DevTools Lighthouse／Performance，各量三次取中位數），記在 [DEPLOY-RECORD.md](DEPLOY-RECORD.md) 第 3 節的「效能」欄。部署後（步驟 11 清快取後）用同樣方式再量一次，**站本身的負載**與**外掛的增量**要分開寫（規格 §13.4）。這些是實驗室數據，不是真實使用者數據（CrUX／RUM），不得當成正式站效能保證。

## 5. 各步驟細節

### 步驟 1：備份

1. 用主機備份功能建立**檔案 + 資料庫**備份（或確認剛剛完成的自動備份），記錄時間點與備份名稱。
2. 確認能下載或有還原入口；只看到「備份成功」訊息不夠。
3. 保存目前外掛清單與版本、首頁 Page ID、選單項目截圖、Header／Footer 管理方式、將要修改的頁面版本。
4. 備份位置只記名稱與位置描述，不寫帳密。

### 步驟 2：上傳同一份 ZIP

1. 後台：外掛 → 安裝外掛 → 上傳外掛 → 選 ZIP → 立即安裝。**先不要按啟用。** 上傳前先確認最大上傳大小夠大（第 2 節末段）。
2. 若主機不允許後台上傳，或最大上傳大小小於 ZIP，由有權限的人用 SFTP 上傳到 `wp-content/plugins/`，內容要與 ZIP 解壓後完全相同；不繞過權限。
3. 核對版本與 SHA-256（第 2 節）。

### 步驟 3：啟用，維持 disabled

1. 啟用 `wg-live`。啟用只寫入預設選項，模式為 `disabled`；不會建立頁面、選單、角色，也不會 flush rewrite。
2. 開「部署資訊」：版本與 build SHA-256 正確、環境類型為 `production`、部署模式 `disabled`、**開發面板為關閉**。
3. 登出視窗開 `/wp-json/wg-live/v1/events`：應為空的 `events`。
4. 查看 PHP 錯誤日誌；開首頁、Store、Account，與部署前截圖比對。

### 步驟 4：建立三個草稿頁面

與 staging 相同（[STAGING.md](STAGING.md) 第 4、5 節）。只建立草稿；不要發布。

1. 建立 `Live`（`live`）、`Listen`（`listen`，父頁 Live）、`Listening Guide`（`help`，父頁 Live）。可使用後台「Live 活動 → 建立建議頁面」子選單（不在設定頁內）：它先做 slug 衝突檢查，只建立草稿，不修改既有頁面。
2. 檢查是否有既有頁面占用這些 slug；有就停下來問授權人，**不覆寫既有頁面**。
3. 每頁用 Elementor Full Width（不是 Canvas），加入一個 Shortcode 元件，放入對應 shortcode。元件 Advanced → Cache 保持 Default／Inactive。
4. 頁面標題只出現一次；保留原站頁首與頁尾，不複製第二份。

### 步驟 5：重新綁定 Page ID

1. 在設定頁選取**正式站**剛建立的三個頁面。從正式站頁面列表取 ID，**不要沿用 staging 的數字**（兩個環境的 ID 不同）。
2. 保存後到「部署資訊」確認三個 Page ID 已綁定、頁面存在。頁面仍是草稿時，「部署資訊」會顯示「未發布」，永久連結欄為「—」，這是預期結果；永久連結（正式網域下的 `/live/`、`/live/listen/`、`/live/help/`）要在步驟 9 發布後才檢查（見步驟 9.4）。
3. 此時部署模式仍為 `disabled`。

### 步驟 6：重新綁定媒體與連結

正式站的資料庫不是 staging 的複本，所以附件 ID 與網址都要重做：

1. 活動的海報：從**正式站媒體庫**選取已核可的圖片（精選圖片）。不要使用來自 staging 的圖片網址。
2. 示範媒體：影片類型的活動（預設）一律播放外掛內建的示範影片（`demo-video-1.mp4`／`demo-video-2.mp4`），設定頁的示範音訊選項不影響它。音訊類型的活動預設使用內建檔案（`demo-tone-1.mp3`／`demo-tone-2.mp3`）；只有在管理者要用自己的核可示範音訊時，才在設定頁選取正式站媒體庫的音訊附件。
3. 檢查所有手動輸入的網址：Account、Store、Contact 覆寫值、商品網址、FAQ 中的連結。「部署資訊」會在這些網址的網域不同於正式站網域時警告。**警告必須清到零，或逐項說明為何保留。**
4. 外掛設定頁 → 站內連結覆寫：把「聯絡連結」設成正式站自己的聯絡頁（例如 `https://<正式網域>/contact/`）或核可的 `mailto:`。聯絡連結**沒有自動值**；不設定時說明頁、停用畫面、取消活動與「無法確認觀看資格」畫面都沒有聯絡連結。儲存後確認「部署資訊」的網域警告為零，並在步驟 9 發布後重測 LINK-CHECKLIST 第 7、9、13 列。
5. 在頁面來源搜尋 `staging`、`localhost`、`127.0.0.1`、`:5173`，應該沒有結果。

### 步驟 7：建立示範活動並切到 demo

1. 新增至少一場明確的示範活動：媒體類型選**影片**（預設）、勾選示範活動、來源類型為「示範」、標題與徽章顯示「介面示範」，**代稱（slug）自己填**，格式 `^[a-z0-9]+(?:-[a-z0-9]+)*$`。不放入任何正式付費來源。
2. 設定可用聆聽模式、時間與時區（Asia/Taipei）。
3. **先取得授權人對公開示範的同意，再把部署模式改為 `demo`。** 發布活動並切到 `demo` 之後，`/wp-json/wg-live/v1/events` 會立即公開示範活動的公開欄位（標題、時間、狀態、模式；不含來源網址）。三個頁面此時仍是草稿，網站上沒有入口連結，但 REST 資料已可被直接請求。若授權人希望完全不公開，就先保留 `disabled`，把「切換到 demo」留到步驟 9 之前一刻。
4. 選取精選活動。

### 步驟 8：草稿預覽檢查

1. 以登入管理者預覽三頁：桌面與手機寬度。
2. 登出視窗無法預覽草稿；改用「預覽」連結或暫時以管理者身分檢查，並另外確認發布後的登出狀態（步驟 12）。
3. 檢查：活動列表、直接開播放頁、兩種模式播放與切換（影片活動要看到畫面且聽到聲音，切換模式時示範影片 1 ↔ 2 會改變）、說明頁；「操作示範音訊，非 Binaural／Atmos 驗證素材」標示與影片畫面內燒入的「操作示範影片…」字幕；開發面板在 `production` **不出現**（含管理者預覽）。
4. 版面：內容寬度、透明頁首避讓、沒有橫向捲動、頁首與頁尾沒有重複。
5. **草稿預覽的連結不完整**：頁面尚未發布時，站內連結不會輸出。活動頁顯示「查看活動資訊」而不是「體驗播放介面」連結，說明連結與返回連結也不會出現。要在預覽中測播放流程，直接開播放頁草稿的預覽網址並加上 `?wg_event=<代稱>`；活動列表 → 播放的點擊流程與所有站內連結，要在步驟 9 發布後檢查。

### 步驟 9：發布三頁

1. 取得授權人核可後，依序發布 Live、Listen、Help。
2. 發布內容仍標示示範或尚未開放；不寫任何「正式上線」「已支援 Atmos 認證」的字樣。
3. 發布後立刻登出視窗打開三個網址，確認顯示正常。
4. 回到「部署資訊」確認三個永久連結都是正式網域下的 `/live/`、`/live/listen/`、`/live/help/`，網域警告為零；再依 [LINK-CHECKLIST.md](LINK-CHECKLIST.md) 重測第 7、9、13 列（聯絡連結）與活動列表 → 播放的點擊流程。

### 步驟 10：導覽與首頁連結

依 [NAV-HOMEPAGE.md](NAV-HOMEPAGE.md) 操作；**只新增項目，不覆寫全站選單，不重建 Header**。若授權人尚未同意公開入口，這步不做，在紀錄寫「未執行：待授權」。

### 步驟 11：清除快取

1. 清除頁面快取（Live 三頁、首頁）以及 CSS／JS 最佳化快取，必要時清 Elementor 的 CSS 再生（Elementor → Tools → Regenerate CSS & Data）。
2. 檢查實際載入的資源網址：
   - 播放頁載入 `…/wp-content/plugins/wg-live/assets/dist/wg-live.js?ver=<hash>` 與 `wg-live.css?ver=<hash>`。
   - 首頁只載入 `wg-live-featured.css?ver=<hash>`，**不載入 `wg-live.js`**。
   - `ver` 值與「部署資訊」的 build 資訊一致，沒有被最佳化外掛移除查詢字串。
3. 最佳化外掛設定：`wg-live*.js` 排除在延遲載入／合併之外（見 NAV-HOMEPAGE.md 第 5 節）。

### 步驟 12：smoke test（登出視窗 + 實際手機）

見第 6 節。

### 步驟 13：保存紀錄

填 [DEPLOY-RECORD.md](DEPLOY-RECORD.md)（版本、commit、SHA-256、時間、被修改的頁面與選單、部署者、備份位置、回復方式、未完成事項），並更新 [HANDOVER.md](HANDOVER.md)。紀錄中不放主機帳密或完整私有串流網址。

可用命令列快速確認（把網域換成正式站）：

```bash
# 活動資料可讀，且不含來源網址
curl -s https://sounds.wgstudiomusic.com/wp-json/wg-live/v1/events

# 播放資格請求不可被共用快取（看 Cache-Control 與 Expires）
# <活動ID> 是示範活動在後台編輯網址中的 post=數字
curl -sI "https://sounds.wgstudiomusic.com/wp-json/wg-live/v1/playback?event=<活動ID>&mode=binaural"

# 頁面來源沒有測試殘留（應無輸出）
curl -s https://sounds.wgstudiomusic.com/live/ | grep -iE "localhost|127\.0\.0\.1|:5173|/@vite|staging"

# 示範影片支援 Range 請求（手機瀏覽器拖曳進度與 iPhone 播放需要）
# 預期：HTTP 206、Content-Range: bytes 0-1/<檔案大小>、Content-Type: video/mp4
curl -sI -H 'Range: bytes=0-1' 'https://<網域>/wp-content/plugins/wg-live/assets/demo/demo-video-1.mp4?ver=0.1.0'
```

規格 §15.4 提醒：「靜態頁面成功但正式站無聲」要檢查是否實際載入正確的 adapter、來源及使用者操作流程，不能只以畫面正常判定成功。smoke test 一定要實際按播放聽到聲音；影片活動還要確認畫面確實在播放（不是只有黑畫面或海報）。

## 7. 部署後驗證

完成第 6 節後：

1. 回到第 3 節的頁面，部署後截圖並與部署前比對。
2. 把結果填入 `evidence/test-results/manual-devices.md` 的 C 表。
3. 兩個環境的紀錄互相引用：staging 通過紀錄 → 部署紀錄 → 交接文件。

## 8. 常見部署情況（規格 §15.4）

| 情況 | 正確處理 |
|---|---|
| 看不到「上傳外掛」 | 由具有適當權限的管理者安裝；不繞過權限，也不把 PHP 塞進文章。 |
| PHP 不相容 | 在 staging 修正程式或協商環境升級；不在正式站臨時升級試運氣。 |
| CSS 未更新 | 檢查版本、載入路徑、快取與 Elementor 生成資源；不先改全站樣式。 |
| 有雙重頁首 | 確認沒有自行複製 Header，檢查頁面版型與 Theme Builder 條件。 |
| shortcode 原樣顯示 | 檢查外掛是否啟用、名稱是否正確、是否用了 Shortcode 元件。 |
| 內容過窄 | 檢查 Elementor 外層容器與元件內層的雙重寬度／padding。 |
| 手機模式面板被遮住 | 檢查 stacking context、overflow 與安全區，不盲目加極大 z-index。 |
| iframe 空白 | 檢查供應商嵌入許可、框架限制與頁面狀態，不將問題一律歸因 CORS。（M1 不使用 iframe 來源。） |
| HLS 在部分瀏覽器無法播 | 分辨來源封裝、編碼支援、跨來源請求、憑證及網路錯誤。（M1 不使用 HLS 來源。） |
| 靜態頁面成功但正式站無聲 | 檢查是否實際載入正確 adapter、來源及使用者操作流程；不能只以畫面正常判定成功。 |

## 9. 只發布頁面時

只發布頁面不需要重新部署整個 WordPress，也不需要切換主題。需要重建永久連結規則時，只在確有路由變更時進行一次，不得在每次請求 flush rewrite（規格 §15.3）。

## 10. 負載測試

300 人容量不屬於 M1 的正式站驗收。若要做頁面、靜態資源與活動資料請求的階梯式負載測試，必須先取得管理者對**該環境與時段**的核可，且不對正式站同時開 300 條串流。工具與限制見 `scripts/load-test.mjs`（需要 `--target` 與 `--approved`，永遠不請求 `/playback` 與媒體）。結果檔寫在 `evidence/test-results/load-<時間戳>.json`。300 人網頁載入成功**不能**證明 300 人 Atmos 直播可承載，那是 M2（規格 §13.5）。
