## 已實作 (implemented)

- `/playback` for an hls source adds `link`: `…/wp-json/wg-live/v1/s/<event>/<token>/<mode>.m3u8` on this site. The token is 16 random bytes (22 characters, base64url), one per user and event, stored in user meta `_wg_live_link_<event>` and the same on every request.
- `GET wg-live/v1/s/<event>/<token>/<mode>.m3u8` (`Stream_Links::rest_open`, no login: VLC sends no cookie) finds the token's owner (exact comparison after the case-insensitive database match), runs `Playback_Provider::resolve()` for that user, and answers `302` to the stream address; `404` for an unknown token or another event; `403` when the owner has no paid order any more or the event is not 直播中／中場休息. Every answer is no-store with no body.
- WordPress answers once per start: the player then fetches the playlists and segments from the stream host (tested with VLC before building: one request to the random address, then playlist, chunklist and `.ts` segments straight from the stream host, 36 s of sound).
- The personal-link panel and Safari's 開始聆聽 (0.5.2) use `link`; the page itself still plays `url`, so the mixed-content rule is unchanged. Uninstall with data deletion also removes the stored links.
- Limits: the player follows the redirect, so the stream address can still be read (Safari's address bar, VLC's log); the stream server accepts anyone until it checks signed links (Wowza SecureToken, M2-PLAN B3b). No admin screen to reset one person's link; no usage log.
